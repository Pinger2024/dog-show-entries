## [ ] 1. (CRITICAL) Cross-org privilege escalation: invitations.send grants secretary/steward/judge role + active membership on ANY organisation with no org-membership check

- **file:** `src/server/trpc/routers/invitations.ts`
- **line:** 19-142 (vuln at 28-64; root cause in assignRole at src/server/lib/utils.ts:32-52)
- **subsystem:** auth/invitations | **verify confidence:** high
- **repro:** 1) Sign in as a legitimate secretary of any club (org A). 2) Open any other club's public show page; the tRPC payload from shows.getById includes organisation.id (org B's UUID). 3) Call api.invitations.send.mutate({ email: <your own account email>, role: 'secretary', organisationId: <org B id> }). Because your user already exists, the existingUser branch runs assignRole and inserts an active membership for you in org B. 4) You now pass verifyOrgAccess/verifyShowAccess for org B — full secretary access to org B's entries, exhibitor PII, refunds, payout bank details (sort code/account number), schedule, sponsors, everything. No acceptance, no email confirmation required for the takeover to take effect.
- **why:** invitations.send is a secretaryProcedure (role-only gate — any secretary of any club passes). It accepts an arbitrary `organisationId` and `role` and never calls verifyOrgAccess to confirm the caller belongs to that org. When the invited email already belongs to an existing user (the common case), it takes the `existingUser` branch (line 40) and immediately calls assignRole(db, existingUser.id, input.role, input.organisationId) with NO acceptance step. assignRole (utils.ts:32-52) blindly INSERTs an `active` membership row for that user in the given organisationId — no permission check whatsoever. The result: an active membership in a victim org, which is exactly what verifyOrgAccess and verifyShowAccess check for. Every sibling org-scoped procedure in this codebase calls verifyOrgAccess (e.g. secretary.listVenues/createOrgPerson/getSponsorNameSuggestions), and updateSecretaryUser even carries an explicit cross-tenant-write-guard comment — proving org-scoping is the intended invariant that this path breaks. The victim org's UUID is trivially obtainable: shows.list and shows.getById are publicProcedures that return the full `organisation` object (with `organisation: true`, shows.ts:199 and 232) including its id, so any visitor to a public show page learns the target organisationId.
- **suggested fix:** In invitations.send, before doing anything with input.organisationId, require it and verify the caller's membership: `if (input.organisationId) { await verifyOrgAccess(ctx.db, ctx.session.user.id, input.organisationId); }` (admins bypass). Better: make organisationId required for org-scoped roles and always verify. Also harden assignRole / accept so a membership can only ever be created for an org the inviter was authorised to invite into (carry the invitedById's org-authorisation through, or re-check at accept time).

## [ ] 2. (HIGH) Secretary manual entry overcharges multi-class entries vs online checkout (different price for identical entry)

- **file:** `src/server/trpc/routers/secretary.ts`
- **line:** 3226-3228, 3279, 3291, 3311
- **subsystem:** Entries & checkout — fees | **verify confidence:** high
- **repro:** On a show with show-level fees (firstEntryFee=500, subsequentEntryFee=300): as secretary, open /secretary/shows/[id]/entries, add a manual postal entry for a dog in 3 classes. createManualEntry stores totalFee=1500 (3×500) and a £15 payment. Enter the same dog in the same 3 classes online via orders.checkout — totalAmount is 1100 (500+300+300). Identical entry, £4 difference; financial report counts £15 for the postal one.
- **why:** createManualEntry prices an entry as `selectedClasses.reduce((sum, sc) => sum + sc.entryFee, 0)` (line 3226) and writes that into entries.totalFee (3279), entry_classes.fee (3291) and payments.amount (3311). It never uses the first/subsequent fee ladder. But every show class's `entryFee` is set to `firstEntryFee` at show creation: the wizard sends `entryFee = firstEntryFee` (src/app/(secretary)/secretary/shows/new/page.tsx:438-442) and shows.ts inserts each class with `feeForDef(id) = entryFee ?? 0` (shows.ts:621,643,656). Meanwhile the exhibitor online path (orders.checkout) prices the SAME dog/classes through computeOrderFees, charging firstEntryFee + subsequentEntryFee×(N-1) (fee-calc.ts:128-136). So a dog in 3 classes with firstEntryFee=£5 / subsequentEntryFee=£3 is charged £11 online but £15 when the secretary records the identical postal/cash entry. The exhibitor is overcharged and the club's financial reports (which sum entries.totalFee) overstate revenue for every manually-recorded multi-class entry. The two creation paths must agree on price. (Note: entries.create at entries.ts:317-320 has the identical sum(sc.entryFee) bug but appears to have no UI caller — same root cause, dead path.)
- **suggested fix:** Route createManualEntry's fee through the shared computeOrderFees service (build a FeeContext from the show's first/subsequent/nfc/JH fees + multiDog config exactly as orders.checkout does at orders.ts:508-535), and write the service's per-entry fee and perClassFees into entries.totalFee / entry_classes.fee / payments.amount. Apply the same fix to entries.create (or delete it if confirmed dead).

## [ ] 3. (HIGH) Stale-order cleanup cancels orders without cancelling the Stripe PaymentIntent → exhibitor can be charged with no entry

- **file:** `src/server/trpc/routers/orders.ts`
- **line:** 319-348
- **subsystem:** Entries & checkout — payment lifecycle | **verify confidence:** high
- **repro:** Open the enter page, reach payment (PI_A created, order A pending_payment) but don't pay. In a second tab, restart checkout — orders.checkout cancels order A (status='cancelled', entries soft-deleted) and creates PI_B. Return to tab 1 and complete PI_A's payment form. Webhook marks payment_A 'succeeded' but order A stays 'cancelled' with deleted entries. Money captured, no entry, invisible to /financial.
- **why:** At the start of every checkout, all of the user's prior pending_payment/failed orders for the show are set to status 'cancelled' and their entries soft-deleted (orders.ts:330-348). The associated Stripe PaymentIntent is never cancelled — there is no `paymentIntents.cancel` call anywhere in the codebase and no payment_intent.canceled webhook handler (grep returns nothing). If that earlier PaymentIntent is later completed (two tabs open, browser back-button with Stripe Elements still mounted, slow 3DS finishing after the user restarted), the succeeded webhook fires: the order is in terminal state 'cancelled' so canTransition is false (route.ts:98-99) and entries are NOT confirmed/un-deleted — yet the payment row is flipped to 'succeeded' unconditionally (route.ts:202-210, gated only on stripePaymentId and not-already-refunded). The money is captured at Stripe but the order stays cancelled and its entries stay soft-deleted. show-metrics scopes all revenue and refund tracking to orders.status='paid' (show-metrics.ts:28, 129-130), so this captured charge appears nowhere in the app — not as club revenue, not as a refund-due item. The exhibitor is charged with no entry and no in-app trace.
- **suggested fix:** In the stale-order cleanup, call stripe.paymentIntents.cancel(order.stripePaymentIntentId) for each superseded order before marking it cancelled (ignore errors if it's already succeeded/uncancelable). Additionally, add a payment_intent.canceled webhook case, and in the succeeded handler, if the order is already in a terminal cancelled state when a payment unexpectedly succeeds, trigger an automatic refund (or at minimum flag it for admin reconciliation) rather than silently marking the payment succeeded.
