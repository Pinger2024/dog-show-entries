# pdf-kit

Shared PDF layout building blocks so pages **adapt to their content**
instead of being hand-tuned per document. Built against 43
`minPresenceAhead` call sites (values 20–150), 100+ `wrap={false}` blocks,
a `SectionTitle` reimplemented in two places, a folio pattern reimplemented
in 11 files, and `Font.register` duplicated across ~10 files — see the repo
CLAUDE.md task brief for the full inventory this generalises.

**Nothing in the codebase has been migrated onto this kit yet.** Existing
pages keep their own hand-rolled fonts/headings/folios/`wrap={false}` blocks
until a migration lands under a golden-render test. This README is for
whoever does that migration, and for anyone building a NEW pdf-kit-based
document today.

## What's here

| Module | Exports | Use it for |
|---|---|---|
| `fonts.ts` | `registerPdfKitFonts`, `registerHankenGrotesk`, `assertFontBudget`, `PDF_KIT_FAMILIES` | Registering Times/Inter/LibreBaskerville once; asserting a document stays within the 3-family budget |
| `measure.ts` | `measureTextWidth`, `estimateLineCount`, `estimateTextHeight`, `fitFontSize` | Deciding sizes/columns/splits BEFORE rendering (react-pdf has no measure-after API) |
| `page-frame.tsx` | `PageFrame`, `Folio`, `NoBorderStyle` | Page size/margins/fixed header+footer/folio in one place |
| `section-title.tsx` | `SectionTitle` | A heading that can't be orphaned at the foot of a page |
| `keep-together.tsx` | `KeepTogether` | A `wrap={false}` block with a real escape hatch for oversized content |
| `fit-text.tsx` | `FitText` | Text that shrinks to fit a width instead of a hand-picked font size |
| `balanced-columns.tsx` | `BalancedColumns`, `balanceColumns` | N columns balanced by measured height, not item count |
| `flow.tsx` | `Flow` | A list of heading+body blocks that never orphans a heading |
| `render-with-page-budget.ts` | `renderWithPageBudget`, `pdfPageCount` | Render → count pages → retry compact if a fixed-page-count document overflowed |

## When to use which

- **Starting a brand new document?** `registerPdfKitFonts()` once at the top,
  wrap every page in `PageFrame` with `folio` on, use `SectionTitle` for
  headings and `Flow` for repeating heading+body sections.
- **A heading keeps ending up alone at the bottom of a page?** `SectionTitle`
  (single heading) or `Flow` (a whole list of heading+body pairs).
- **A block must never split, but sometimes might be too tall for a page?**
  `KeepTogether` with `estimatedHeight`/`maxHeight` from `measure.ts` — plain
  `wrap={false}` alone silently overflows the page instead of paginating.
- **A name/title might be too long for its box?** `FitText`, not a
  hand-picked font size.
- **A list (officials, sponsors, an exhibitor index) needs to split across
  2–3 columns evenly?** `BalancedColumns` — never `Math.ceil(n / columns)`.
- **A document has a designed page count that data-elastic content might
  overflow?** `renderWithPageBudget` (generalises
  `src/server/services/schedule-render.ts`'s `renderScheduleWithFit`, which
  is now a thin wrapper over this).

## The fixed-footer border rule

**Never put a border directly on a `fixed` element.** A `fixed`
absolute-positioned footer that also carried a `borderTopWidth` has
previously shipped a rule line whose Y coordinate grew geometrically across
a document's pages — a real production bug. `PageFrame`'s
`headerStyle`/`footerStyle` are typed `NoBorderStyle` (every border
property omitted) so this is a compile error, not a runtime one:

```tsx
// ❌ Type error — NoBorderStyle rejects borderTopWidth
<PageFrame footerStyle={{ borderTopWidth: 1 }} ... />

// ✅ Put the border on a plain, non-fixed child nested inside the slot
<PageFrame
  footer={
    <View style={{ borderTopWidth: 0.5, borderTopColor: '#ccc', paddingTop: 4 }}>
      <Text>Generated by Remi</Text>
    </View>
  }
/>
```

The rule applies to `Folio`'s own `style` prop too, and to anything else you
mark `fixed` yourself outside `PageFrame`.

## The 3-font-family rule

`@react-pdf/renderer` 4.3.2 (pinned) has a confirmed bug: a document using a
**4th distinct font family** corrupts an unrelated page's font resources
elsewhere in the same document — `pdffonts` reports it embedded correctly,
but poppler fails a page with "Unknown font tag" / "No font in show/space".
Full writeup in `src/lib/pdf-fonts.ts`. Consequences for this kit:

- `registerPdfKitFonts()` only ever registers Times, Inter, LibreBaskerville.
- `HankenGrotesk` is registered separately (`registerHankenGrotesk()`) and
  must **never** share a document with the other three, or with any other
  family. It is only proven safe on the SV/WUSV schedule+catalogue and the
  standalone secretary report PDF.
- Call `assertFontBudget([...])` with the families a document actually uses
  — it throws in dev if you exceed 3, or if you mix HankenGrotesk with
  anything else, so a future edit that quietly adds a 4th family fails loud
  instead of corrupting a printed catalogue.

## The decorative-glyph rule

A decorative glyph (✂) that an embedded font lacked pulled in an unembedded
Helvetica fallback for that one glyph — same "unembedded base-14 font"
print-preflight failure class as `src/lib/pdf-pad.ts`'s documented base-14
phantom-reference issue. Don't reach for a Unicode symbol on the assumption
a TTF carries it; use plain ASCII (`X` not `✗`) or an inline image.

## A react-pdf limitation this kit's tests found (matters for migration)

**`minPresenceAhead` stops working if the element carrying it is nested
inside even one extra wrapping `View`.** Found building `Flow`: wrapping
each `{heading, body}` pair (or the whole list) in its own container made
`minPresenceAhead` have **zero effect at any magnitude** (swept
1/5/14/28/100/300 points — identical, broken result every time). Once the
wrapper was removed (`Flow` renders a flat `React.Fragment` per block, no
container of its own), the prop's magnitude started mattering again exactly
as documented. Practical upshot: `SectionTitle`, `Flow`, and any
`minPresenceAhead` usage you write must be a **direct child of the page's
own flow** (a `<Page>`/`<PageFrame>`, or another container that isn't
itself isolating its children) — not nested inside a styling wrapper you
added "just to group things." This is exactly the kind of thing to check
first if a migrated heading stops respecting its keep-with-next protection.

## `undefined !== omitted` for `minPresenceAhead` (and `wrap`, `break`)

`@react-pdf/layout` reads several of its pagination-affecting props with the
`in` operator, not a nullish check — e.g. `getMinPresenceAhead = (node) =>
'minPresenceAhead' in node.props ? node.props.minPresenceAhead : 0`. A prop
key that is *present* with value `undefined` (which is exactly what
`<View minPresenceAhead={someOptionalVar}>` produces when the caller didn't
supply one) reads back as `undefined`, **not** the documented default of
`0` — and `top + height + marginBottom + undefined` is `NaN`, which
silently disables react-pdf's own protection against a trailing margin
being cut off at a page boundary (`Math.min(NaN, x)` is always `NaN`, and
every comparison against `NaN` is `false`). `KeepTogether` had exactly this
bug until the front-matter-on-kit migration found it live: a bare
`<KeepTogether>` (no `minPresenceAhead` passed) was meant to be identical
to the `<View wrap={false}>` it replaces, but reflowed page breaks on two
real shows' catalogues with no other code change. Fixed by only spreading
the prop when the caller actually supplies a value — see
`keep-together.tsx` and its "never leaks an undefined minPresenceAhead
prop key" test. **Any new prop you forward optionally onto a `<View>`,
`<Text>`, or `<Page>` — not just `minPresenceAhead` — needs the same
treatment if react-pdf's layout engine reads it with `in` rather than
`!= null`** (`break` is read the same way; `wrap`'s generic child-splitting
reader `getWrap` is too, though `PageFrame`'s own `wrap` pass-through
happens to be safe because top-level page pagination checks
`page.props?.wrap === false` directly instead of going through that
generic reader — verified by reading `node_modules/@react-pdf/layout`,
not assumed).

## Testing pattern

Every component here is tested against a REAL `renderToBuffer()` output,
inspected with poppler (`pdftotext -bbox-layout` for line/word positions,
`pdffonts` for embedding) via the shared `__tests__/poppler.ts` helper —
never by asserting on the React element tree. Several of this kit's own
tests are constructed as a precise adversarial crossover (a spacer `View`
sized, by linear search, to the exact point where an unprotected heading
would land alone at the foot of a page) rather than hoping a naturalistic
document happens to hit the bug by chance — see `section-title.test.tsx`
and `flow.test.tsx` for the technique, including a case (the "realistic
24-section document" smoke test) where the naturalistic version did NOT
happen to catch a real regression that the precise version did.
